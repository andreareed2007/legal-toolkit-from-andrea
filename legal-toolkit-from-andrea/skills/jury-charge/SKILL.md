# Jury Charge Skill

## Purpose and the two failure modes this skill exists to prevent

1. **Hallucinated pattern language.** A jury charge drafted from a model's training-data approximation of pattern-instruction text — rather than the verbatim published text — produces a charge riddled with verification items, each a potential appellate error. Therefore: **no question, instruction, or definition is drafted unless its verbatim pattern-section text was printed by `scripts/pjc_lookup.py` in the current session.** Pattern language from memory is prohibited, even for sections that "obviously" say something. This applies identically to every jurisdiction's library.
2. **Routing cascade errors.** One stale question number in an "If you answered..." instruction silently corrupts every downstream answer and can make a verdict reversible. Therefore: **the routing map is data (`charge map JSON`), routing prose is generated by `scripts/routing_map.py render`, and the final charge text is machine-checked against the map by `crosscheck`.** Never hand-write or hand-edit a routing instruction.

## Jurisdiction gate (runs inside Phase 0)

Ask which jurisdiction's pattern instructions govern (AskUserQuestion). Then:

- **Library exists and is validated** (registry `libraries.json` under the configured `jury_library_root`): proceed, passing that library path to every `pjc_lookup.py` call. The library's `library.json` supplies the citation label (PJC, CACI, ...), index/matrix filenames, and coverage note.
- **Library missing or `validated: false`:** STOP drafting. Offer to build it via `scripts/build_library.py` following `references/JURY_CHARGE_LIBRARY_BUILDER.md` — official source only, staged by the user, parsed, spot-checked, and attorney-approved before first use. `pjc_lookup.py` mechanically refuses unvalidated libraries (exit 3). No library, no charge — never draft instructions from memory for an unsupported jurisdiction.
- Routing phrasing follows the charge map's `routing_style`: `tx` (proven live) or `ca-vf` (first cut; the audit flags it — verify against the jurisdiction's official verdict forms before filing).

## Where libraries live

The toolkit stores one user profile at `~/.legal-skills/config.json` (see the `environment-setup` skill). Its `jury_library_root` key points at the folder that holds every jurisdiction's library plus the `libraries.json` registry (default `~/.legal-skills/jury-instruction-libraries/`). **The shared skill ships with ZERO libraries.** Every first-time user is routed to the builder to stage and validate their own copy of whatever pattern-instruction resource governs their case:

- Some sources are freely published by the court of record (e.g., California CACI is a free Judicial Council PDF; several federal circuits publish pattern instructions at no charge) and may be fetched from the official publication.
- Others are commercial or bar-copyrighted (e.g., the Texas PJC) and CANNOT be fetched — the user must supply a licensed copy, staged into the builder by hand.

Either way the library is built, spot-checked, and attorney-approved through `build_library.py` before `pjc_lookup.py` will read it. Libraries never ship inside the package; only the parser and builder pipeline do.

## The five phases (gates are mandatory)

**Phase 0 — Posture.** Jurisdiction gate (above). Court type (tx-state / business / federal / ny-state / ca-state), charge posture (requested vs. court's charge), locate the matter's claim summary. List every open attorney question (mooted claims, DJ/equitable submissions, stricken defenses) and ask the user before drafting. AskUserQuestion, not assumptions.

**Phase 1 — Claim map.** Every claim, by every party, against every party; defenses attach to claims, not globally. Check each claim against the library's claim matrix (`pjc_lookup.py --list-claims`); surface every `ATTORNEY JUDGMENT` flag as a question to the user. A machine-drafted matrix (new jurisdiction) is a finding aid only — every entry needs the attorney's curation before use.

**Phase 2 — Pattern lookup (THE GATE).** For every claim: `python3 scripts/pjc_lookup.py --library "<library path>" --claim <CLAIM_ID> --ledger <matter>/pjc_ledger.json`. Read the printed verbatim text. Follow and read every cross-reference. Exit code 2 = section not indexed = STOP and tell the user. Exit code 3 = library not validated = STOP; run the builder gates first. The ledger is the source-audit input; a section not in the ledger may not appear in the charge.

**Phase 3 — Routing map.** Build the charge map JSON per the schema (stable string keys, never question numbers; `sources` or legacy `pjc` for section ids; set `source_label` and `routing_style` for non-Texas jurisdictions). Run `routing_map.py validate <map>` — fix every ERROR, justify every WARNING in the node's `notes`. Do not draft on a failing map.

**Phase 4 — Draft.** `routing_map.py render <map> -o skeleton.md --numbering <numbering.json>` assigns question numbers and generates all routing instructions. Populate each `[POPULATE FROM VERBATIM ... TEXT]` slot from the Phase 2 text, substituting party names/facts only where the pattern brackets call for it; any deviation from pattern language gets a footnote flag. Footnote every question to its pattern section or statute ("No pattern exists; the instruction tracks the statutory elements."). Requested posture: GRANTED/REFUSED line after every item. House style: smart quotes, one space after periods.

**Phase 5 — Verify and assemble.** Three audits: completeness (every claim/defense → question number or documented omission), pattern source (drafted text vs. ledger sections), routing (`routing_map.py audit <map> -o <audit.html>` — this HTML ships with the charge). Then `routing_map.py crosscheck <map> --numbering <numbering.json> --charge <extracted charge text>` on the FINAL text — paste the TOTALS line; any mismatch means re-render, never hand-fix. Assemble the .docx through the **court-filing skill** (read its SKILL.md and the court-type module; the charge body is content, the caption/title/signature/certificates/spacing are court-filing's domain) and run `validate_court_filing.py --court-type <type> --spacing <single|double>`; paste that TOTALS line too. Not 0 failures = not finished.

**Phase 6 — Remediate.** Audits produce findings, findings produce an amended charge. All audit results flow into one ledger: `routing_map.py validate/crosscheck --findings <ledger.json>` appends automatically; language-audit and manual findings go in via `scripts/findings.py add/import` (categories: MISSING_ELEMENT, WRONG_CITE, CONFLICTING_DEFINITION, MISSING_INSTRUCTION, ROUTING, ARCHITECTURE, NO_SOURCE, ATTORNEY_DECISION). For each finding, draft the fix with `findings.py propose` — replacement language comes ONLY from the verbatim pattern text already read in Phase 2, never from memory. Then the gate: `findings.py report -o <fix_proposal.html>` goes to the user, and every finding needs a disposition (`findings.py disposition <id> approved|rejected|modified|deferred`) before anything is applied. `findings.py status` exits 2 while any critical finding is pending — do not draft past it. Apply approved fixes (map first for routing; track-changes protocol for filed charges), then re-run ALL audits and the court-filing validator. Fingerprint dedupe means rejected findings never resurface as new. The ledger replaces the punch list.

## Renumbering protocol

Add/remove/reorder questions by editing the MAP, then re-render and re-crosscheck. Question numbers and routing prose are disposable outputs. Never edit a number in prose. (This replaces the old `@@N@@` collision-avoidance pattern.)

## Known limitations (state them when relevant, don't work around silently)

- Mixed OR-predicates + defense-block on one node all join with "and" in generated prose; if a node needs "(A or B) and not-C" routing, split the node or flag for manual pattern-conformant phrasing, and note it in the audit.
- `crosscheck` parses English routing sentences by regex; exotic hand-crafted conditionals may not parse — which is itself a signal they should have been generated.
- A library's index covers only the volumes that have been parsed and validated into it. A claim needing an un-parsed volume STOPS the lookup (exit 2) — stage and parse that volume through `build_library.py`; never substitute memory.
- `ca-vf` routing style is a first cut — not yet used in a live matter. Verify generated phrasing against the matter's official verdict forms; extend the style rather than hand-editing prose.
- `build_library.py parse` supports `caci-pdf` as its reference format. A new jurisdiction's format means writing a parser from the actual official document, then passing the spot-check gate.

## Shareability rule

The skill's logic is jurisdiction-agnostic. **Libraries never ship** — bar-copyrighted sets (e.g., Texas PJC) cannot be redistributed, and even freely published sets (CACI) stay out of the package. Recipients build their own libraries through the builder gates.

## Deliverables (every run)

1. Filing-ready charge .docx (court-filing pipeline, validated, TOTALS pasted).
2. Conditional-routing audit HTML (`routing_map.py audit`), with crosscheck TOTALS.
3. Findings ledger + Fix Proposal report (`findings.py report`) when auditing or amending an existing charge, with `findings.py status` TOTALS.
4. Updated claim map + charge map JSON + numbering map + pattern-source ledger, saved to the matter folder.
5. When a library was built or extended: the library folder with manifest history, parse report, and spot-check approval on record.
